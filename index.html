▶️ 1. How to run it end to end

All code is in the GitHub repository: numbered SQL scripts in sql/, Python steps in py/, reports in reports/. To rebuild everything from the raw CSVs:

  1. Clone the repository and run pip install duckdb openpyxl (Python 3.9+)
  2. Put users.csv, transactions_export_1.csv, transactions_export_2.csv and churn_labels.csv in data/ at the repository root
  3. Run python run_all.py from the repository root. It runs every sql/NN_*.sql in order into tune.duckdb (~20 s), then every py/NN_*.py, which rewrites the Part 1a reports

The repository holds no data/ folder and no database: all paths are relative, so the scripts run on your own copy of the CSVs

Six layers, in this order. Each one only reads the layers before it. churn_labels needs no cleaning (no duplicates, no invalid values), so it is used as delivered.

1b · GrainChoose the subscription table's grain and explain why

Grain: Period + episode_id

Chosen: fct_subscription has one row per billing period, and every row carries episode_id

Why Period + episode_id

  • Monthly revenue, ARPU and discounts (Part 2): shows how much money came in each month and how price or discount changed from period to period
  • Plan changes (Upgrade / Downgrade): every billing period can be compared to the previous one, as the brief asks
  • Keeps the Episode advantage: episode_id identifies reactivation (Reactivated) and when a new subscription run starts

Trade-off

  • Bigger table: 5,501,434 periods instead of 748,144 episodes
  • The length of a whole subscription run needs GROUP BY user_id, episode_id instead of reading one ready row

Why we still chose it

  • One-way aggregation (lossless vs lossy): from Period + episode_id you can always go up to Episode with a simple GROUP BY; collapsing to Episode first deletes the monthly detail and plan changes, and they cannot be rebuilt from that table
  • Low running cost vs lost flexibility: with episode_id ready on the table and a modern engine (DuckDB), keeping the detail costs little (size, run time); choosing Episode would force rebuilding the model from the raw layer

Options compared

Key fact behind the dates: expires_at is the membership expiry after the event, not the plan’s own end. An early renewal stacks its days on top of the old expiry, so each period also gets non-overlapping covered_start / covered_end (0 overlaps). A new episode starts when the gap after expiry is more than 30 days

+ Known limits

What the rules cannot settle
  • The same-day order (cancel before purchase) is a rule, not a fact: the files have no timestamp or event ID. It is documented, deterministic and has one data-driven exception (a cancel on the first purchase day, issue 11)
  • T16/T17 derived expiries use purchase date + plan days. For an early renewal the true expiry would be later; this affects 1,691 rows
  • March-2017 churn is censored by construction (the 30-day window needs April data). Billing's labels use April data we don't have; Part 1c deals with that
  • Cancel-row amounts (160,720 rows, 23.2M) are read as the cancelled plan's price, not a payment: interpreted, not documented. If billing confirms they are refunds, revenue needs a negative adjustment
  • Left-censoring: data starts 2015-01-01, so the 133,585 users first seen in Jan 2015 may have subscribed earlier. Their "new" is flagged (flag_first_seen_jan2015); Jan-2015 new counts must not be read as acquisition

3a · ConfoundingWhich factors only look like they matter because of confounding

Age is a mirage

Under-25s churn 2–3× more, but only 33–54% of them use auto-renew (vs 84–90% of users 25 and older). With the same payment mix, every age band churns 4.2–5.6%

Channel is mostly mix too

Channel 4 churns 8× more than channel 7 as it looks. Channel 7 users are 99% auto-renew, channel 4 only 38%. With the same mix the gap shrinks to about 1.5×

The first renewal is the riskiest moment

16.5% leave at their first renewal, then churn settles at about 4%. It is not just payment mix: even with auto-renew, first-timers churn 8.7% vs about 2% later. Tenure is a real driver

Tenure = months since the user's first paid subscription. Users who paid before 2015 show a shorter tenure than they really have

+ Plan length: per renewal vs per month

Long plans lose more per renewal, far less per month

All long plans are paid manually, so we compare manual payers only. A 12-month plan loses 30.7% at renewal, but that renewal comes once a year: 2.7% a month, vs 18.5% a month on manual 30-day plans. Plan length only looks bad when you count renewals, not months

Per month = 1 − (1 − churn per renewal)30 / plan days. People who choose a yearly plan may be more committed to begin with, so this is not proof that annual plans keep people (see Part 5a test)

+ How we measured

One row per paid renewal that came due: a paid subscription period whose expiry falls in 01-16 – 02-17 (mart_renewal_decisions, 3,035,012 rows; 2,995,689 after removing the incident). Churned = no new purchase within 30 days of expiry (the brief's rule; early renewal counts as staying). Fair comparison = the churn a group would have with the average auto-renew and plan mix (observed ÷ expected × 4.6%). Free trials and cancellations are not used as drivers: a trial ending is a conversion, and a cancellation is the churn

5a · SQLOptional: the SQL to analyze the test

+ Analysis SQL

Runs on the clean layer plus a hypothetical experiment_assignments(user_id, variant, assigned_at) table; tested on a fake assignment

with a as (
  select e.user_id, e.variant, e.assigned_at::date as d0, max(s.is_auto_renew) as is_auto_renew
  from experiment_assignments e
  left join fct_subscription s
    on s.user_id = e.user_id and e.assigned_at::date between s.start_date and s.end_date
  group by all
), u as (
  select a.user_id, a.variant, a.is_auto_renew,
    max((s.plan_days >= 360 and s.start_date between a.d0 and a.d0 + 37)::int)            as took_annual,
    max((s.is_free = 0 and s.start_date between a.d0 and a.d0 + 37)::int)                 as renewed,
    coalesce(sum(s.amount_paid) filter (where s.start_date between a.d0 and a.d0 + 364), 0) as cash_12m,
    coalesce(sum(s.amount_paid * greatest(0, least(s.end_date, a.d0 + 90) - greatest(s.start_date, a.d0))
                 / nullif(s.end_date - s.start_date, 0)), 0)                               as earned_90d
  from a left join fct_subscription s on s.user_id = a.user_id and s.start_date >= a.d0
  group by all
), g as (
  select is_auto_renew, variant, count(*) n, avg(took_annual) take_up, avg(renewed) renewal,
         avg(cash_12m) cash, var_samp(cash_12m) v, avg(earned_90d) earned_90d
  from u group by all
)
select t.is_auto_renew, t.n n_treat, c.n n_ctrl, t.take_up, c.renewal ctrl_renewal, t.renewal treat_renewal,
       t.cash - c.cash as cash_diff,
       (t.cash - c.cash) / sqrt(t.v / t.n + c.v / c.n) as z_score,   -- |z| > 1.96 = significant
       t.earned_90d - c.earned_90d as earned_90d_diff
from g t join g c on c.is_auto_renew = t.is_auto_renew and t.variant = 'treatment' and c.variant = 'control';
