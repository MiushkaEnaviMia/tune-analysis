## How to read this report

- **Check IDs.** Every finding comes from one check in `sql/01_data_quality.sql`. The letter names the table: **T** = transactions (both billing exports, combined as base_transactions); **U** = users (the user registry, users.csv (raw_users)); **L** = churn_labels (billing's churn labels for March 2017, churn_labels.csv (raw_churn_labels)). The number is only the check's position. The full list of checks and the names used in the text are in the legend at the end of this section.
- **Leadership questions:** **Q1** subscriber-base health & trend; **Q2** churn drivers; **Q3** free trials & price points; **Q4** annual plans.
- **Severity** (how much the answers change if the issue is ignored):
  - **Critical:** If ignored, a headline answer is wrong (e.g. the active base or annual-plan counts).
  - **High:** If ignored, at least one leadership question is clearly distorted.
  - **Medium:** Distorts one cut or the churn rule; handled in the clean layer.
  - **Low:** Small or narrow; a simple rule and a flag handle it.
- **Type:**
  - **Data Bug:** Values missing or wrong: can be flagged or estimated, not fully restored.
  - **Analytical Gotcha:** Values correct but misleading; one rule handles it fully.
- **Fix** (can it be repaired?):
  - **Full:** Fully handled in the clean layer.
  - **Partial:** Estimated or flagged; some doubt remains.
  - **None:** Cannot be repaired; shown as 'Unknown' or replaced by our own rule.
- **Order:** severity first (how much the answers to Q1-Q4 change if the issue is ignored). Within the same severity, Data Bugs come first, because they cannot be fully fixed.
- **Options A / B:** two realistic fixes per issue. B is chosen; 'Why B over A' gives the reason.

### 1. Billing's churn labels cover different users than those due to expire in March 2017 (the brief's rule)

- **Severity:** Critical. **Type:** Data Bug. **Fix:** None. **Questions hit:** Q2 (churn drivers); Q4 (annual plans).
- **Checks** (rows): **L6** labelled but not 'due in March': 26,126 · **L7** 'due in March' but unlabelled: 6,061 · **L4** labelled user, no transaction by 2017-02-28: 639
- **What is broken:** Built from each user's last transaction up to 2017-02-28, the 'due in March' set and the labels disagree: some labelled users fall outside it (L6), some users in it are unlabelled (L7), and 639 labelled users have no transaction up to 2017-02-28 (L4).
- **Size (L6):** 26,126 rows (10.81% of churn_labels), 26,126 users (10.81%).
- **Why it matters:** These are billing's labels for its April 2017 churn review, most likely the churn number leadership has already seen. Part 1c shows they break their own rule (early renewals and renewals after 90+ days labelled churned; cohort built from export_1 only), so the labelled churn rate is overstated and biased against long plans (Q2, Q4). They cannot be repaired from the data, only replaced by our own implementation of the rule. They are also the yardstick for validating that rule (1c).
- **How found** (returns 26,126 rows, validated against L6):

```sql
SELECT * FROM raw_churn_labels
WHERE user_id NOT IN (SELECT user_id FROM due_mar);  -- due_mar: view in 01_data_quality.sql
```

| Option | Approach | Run cost | Storage | Speed / latency | Data-loss / bias risk | Verdict |
|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| A: Use billing's labels as the churn target | Take is_churn as ground truth for the driver analysis; skip our own definition. | None | None | Immediate | Medium: one cohort only (March 2017), no trend for Q1/Q2, and the population gaps (L6/L7) are inherited unexplained | Rejected |
| B: Implement the brief's rule, report disagreement | Independent implementation over all months; confusion matrix vs the labels on March 2017; explain each disagreement bucket. | One query + review | None | Seconds | None | **Chosen** |

- **Why B over A:** Our own rule runs on every month (trend) and the labels stay an independent check of it, instead of an unverified input.
- **Decision:** Implement the definition independently in 1c; report and explain the disagreement buckets.

### 2. Paid purchases logged with plan length 0 and list price 0, Mar-Oct 2015: 16.7% of paid purchases in those months, 39.7% of active users

- **Severity:** Critical. **Type:** Data Bug. **Fix:** Partial. **Questions hit:** Q1 (subscriber-base health & trend); Q3 (free trials & price points); Q4 (annual plans).
- **Checks** (rows): **T9** paid rows missing plan length and list price: 214,207
- **What is broken:** payment_plan_days = 0 and list_price = 0, but amount_paid > 0 (194,047 rows paid 149) and expires_at is about 1 month later. All rows fall in 2015-03 to 2015-10: a logging gap in the billing system, not free plans. Date evidence: 86.4% end 25-35 days after the purchase (normal paid 30-day rows: 90.1%); the 1,031 rows paid 1,788 run a median 413 days, i.e. annual plans.
- **Size (T9):** 214,207 rows (3.74% of transactions), 122,393 users (20.2%).
- **Why it matters:** In Mar-Oct 2015 these rows belong to 39.7% of active users (121,000 of 305,113). Treated as 0-day plans they create no subscription period, so that share of the base vanishes from the 2015 trend (Q1). Left as is, 2015 also shows 0-day plans, a negative discount (paid > list) and broken ARPU per plan. That corrupts the 2015 baseline for the trend (Q1), price points (Q3) and plan mix (Q4).
- **How found** (returns 214,207 rows, validated against T9):

```sql
SELECT * FROM base_transactions
WHERE payment_plan_days = 0 AND list_price = 0 AND amount_paid > 0;
```

| Option | Approach | Run cost | Storage | Speed / latency | Data-loss / bias risk | Verdict |
|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| A: Price-to-plan lookup | Map amount_paid to the plan sold at that price in the same period (149 -> 30 days, 1,788 -> 410 days ...); list_price = amount_paid; flag. | One small mapping table + join | +1 lookup table, +1 flag | Seconds | Medium: needs a hand-built price list; prices that map to several plans or appear only in 2015 stay unknown | Rejected |
| B: Plan days from the row's own dates, snapped + flag | plan_days = expires_at - transacted_at, snapped to 7/30/90/180/365/410; list_price = amount_paid; is_imputed_plan = 1. Rows with negative date gaps (1,698) fall back to the price lookup. | One CASE expression | +1 flag column | Seconds | Low: 2015 discount set to 0; flagged, so it can be excluded | **Chosen** |

- **Why B over A:** The expiry is what billing actually granted on that row, so it carries the plan length without a hand-maintained price list, and it also catches the annual rows. The price lookup stays as the fallback for the few rows with unusable dates.
- **Decision:** Impute plan days from dates (price lookup as fallback), set list_price = amount_paid, flag every imputed row. Ask billing for a backfill.

### 3. The two exports are split by expiry date, not purchase date: 89,728 older purchases exist only in export_2

- **Severity:** Critical. **Type:** Analytical Gotcha. **Fix:** Full. **Questions hit:** Q1 (subscriber-base health & trend); Q4 (annual plans).
- **Checks** (rows): **T2** old purchases in export_2: 89,728 · **T1** export_1 rows expiring after March 2017: 0 · **T3** long plans only in export_2: 15,731
- **What is broken:** export_1 contains only rows with expires_at <= 2017-03-31: T1 finds 0 rows expiring later. export_2 contains every row expiring after that: 266,538 March 2017 purchases plus 89,728 purchases made 2015 - Feb 2017. Neither file is complete on its own.
- **Size (T2):** 89,728 rows (1.57% of transactions), 65,306 users (10.78%).
- **Why it matters:** Reading export_2 as 'the March file' drops every subscription bought earlier that is still alive after March 2017. That undercounts the active base at period end (Q1) and hides almost all recent annual plans: 10,228 of the 10,291 410-day plans bought Aug 2016 - Feb 2017 sit in export_2 (Q4).
- **How found** (returns 89,728 rows, validated against T2):

```sql
-- export_2 rows bought before March 2017 (lost if export_2 is read as 'March only')
SELECT * FROM base_transactions WHERE src_file = 2 AND transacted_at < 20170301;
-- proof of the split: export_1 never expires after 2017-03-31
SELECT src_file, max(expires_at), count(*) FILTER (WHERE expires_at > 20170331) FROM base_transactions GROUP BY 1;
```

| Option | Approach | Run cost | Storage | Speed / latency | Data-loss / bias risk | Verdict |
|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| A: Incremental append: export_1 + March rows of export_2 | Standard monthly-load pattern: export_1 is history, export_2 is the new month; append export_2 rows with transacted_at >= 2017-03-01. | Lowest (filtered append) | Lowest | Fastest; fits a daily/monthly incremental job | High: silently loses the 89,728 older export_2 rows, incl. 10,228 annual plans | Rejected |
| B: Full UNION of both exports + lineage + conflict rules | One table with src_file and src_row (which file and row each record came from), then the duplicate and conflict rules of T4 (same event, conflicting versions across exports), T7 (exact duplicate rows) and T24 (stacked purchases). | +1 scan of 5.7M rows (about 1 s in DuckDB) | +2 small columns (TINYINT, BIGINT) | Seconds; full reload each time | None; 747 conflicting rows resolved by an explicit rule | **Chosen** |

- **Why B over A:** The append pattern is right only if the files are split by transaction date. They are split by expiry date, so the append loses rows by construction. A full reload costs about one second at this size.
- **Decision:** UNION both exports; keep src_file/src_row for audit. Ask billing for one export with an event ID and updated_at.

### 4. Users who pay or transact but are missing from users.csv (8.3% of revenue)

- **Severity:** High. **Type:** Data Bug. **Fix:** Partial. **Questions hit:** Q1 (subscriber-base health & trend); Q2 (churn drivers).
- **Checks** (rows): **T23** users missing from users.csv: 697,306 · **L5** labelled user missing from users.csv: 27,606
- **What is broken:** 109,330 users with transactions (18.05% of transacting users; 697,306 rows) have no row in the user registry. They carry 71.7M of revenue (8.3% of 862.6M); 53,023 of them paid at least once. 27,606 labelled users are also missing, and they are not a random subset: they churn at 5.2% vs 9.4% for the 214,059 labelled users found in the registry.
- **Size (T23):** 697,306 rows (12.18% of transactions), 109,330 users (18.05%).
- **Why it matters:** An inner join to users silently drops 18% of transacting users and 8.3% of revenue from every metric (Q1). Because the missing users churn at about half the rate of the rest, an inner join also biases the churn rate and every churn-driver cut (Q2). Their attributes (age, channel, city) are unknown, so segment cuts cover only part of the base. It ranks below the Critical issues because it does not lose rows by itself (revenue and actives come from transactions), but any join to users silently changes both the totals and the churn answer.
- **How found** (returns 697,306 rows, validated against T23):

```sql
SELECT * FROM base_transactions
WHERE user_id NOT IN (SELECT user_id FROM raw_users);
```
